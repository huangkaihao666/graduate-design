基于多智能体协同与RAG架构的社交化生活决策辅助平台

### 项目背景与核心理念：UGC“生活决策与道德法庭”多智能体众包辩论平台

普通人每天都在面临两难选择（如“被老板PUA要不要裸辞？”、“伴侣送了很丑的礼物要不要直说？”、“遇到奇葩室友怎么优雅回击？”）。传统的知乎、小红书等社区回复太慢、容易沉底，且往往充满主观情绪和戾气。本项目旨在打造一个由“人类+AI智能体”共同组成的决策众包平台，为用户提供即时、多维、且极具情绪价值的解决方案。

**平台玩法（双边市场模型）：**

- **求助者**：发布自己的生活困境或人际冲突。
- **吃瓜群众/智囊团**：其他普通用户可以实时围观，并给不同的AI智能体“投票”或补充人类观点。
- **核心机制**：平台会自动为该困境拉起一个“多智能体陪审团”（例如：扮演“毒舌现实主义者”、“温柔共情者”、“绝对理性的律师”的多个AI）。它们在后端工作流的控制下进行激烈的交叉辩论，最终给求助者输出一个多维度的行动建议。

**AI技术深度结合点：**

- **向量数据库（RAG）**：存储海量的心理学效应、博弈论模型、法律常识及平台过往的高赞历史决策。Agent在辩论时需不断从RAG中引经据典，确保言之有物。
- **多\*\***智能体\***\*博弈（Multi-Agent Debate）**：这是核心亮点。设定不同Agent的Prompt和立场，让它们互相反驳（Cross-examination），穷尽不同视角的可能性。
- **大模型\*\***工作流\***\*（\*\***Workflow\***\*）**：控制辩论的轮次（开场陈述 ➡️ 自由辩论 ➡️ 总结陈词），并允许围观的人类用户在特定节点随时“插嘴”干预工作流。

### 一、 核心技术架构与可行性分析（重构版）

#### 1. AI 层的正确实施方式：后端编排模式 (Backend Orchestration)

不要试图用一个 Coze 工作流搞定所有事。正确的做法是：

- **在 Coze 上创建 3 个独立的 Bot（并在每个 Bot 内部绑定专属的 Coze \*\***工作流\***\*以增强复杂处理能力）**：
  - `Bot A (毒舌现实主义者)`：挂载“社会学/博弈论”知识库（RAG）。**内部调用“反伪善拆解\*\***工作流\***\*”**：该工作流包含大模型节点和代码节点，专门提取用户描述中的“逻辑漏洞”和“隐藏利益动机”，处理后返回给 Bot A 作为毒舌反击的弹药。Prompt 设定为犀利、直击痛点。
  - `Bot B (温柔共情者)`：挂载“心理学/非暴力沟通”知识库。**内部调用“情绪画像分析\*\***工作流\***\*”**：该工作流通过大模型节点分析用户的潜在情绪状态（如焦虑、自责），并匹配 RAG 库中的安抚话术模板，指导 Bot B 生成提供心理支撑的回复。
  - `Bot C (理智律师)`：挂载“民法典/劳动法”知识库。**内部调用“法律要素提取与溯源\*\***工作流\***\*”**：该工作流强制提取案情中的时间、地点、金额、合同状态等关键要素，若要素缺失则触发追问逻辑，若齐全则去 RAG 库精准检索法条原文，确保 Bot C 只讲客观事实和法律风险。
- **在 NestJS 中实现 \*\***Workflow\***\*（辩论流转引擎）**：
  - 用户发布困境后，NestJS 充当“法官/主持人”。
  - **Round 1**：NestJS 并发调用 Bot A 和 Bot B 的 API（传入用户的困境），获取它们的独立观点。
  - **Round 2 (交叉辩论)**：NestJS 将 Bot A 的观点发给 Bot B（“刚才毒舌说应该立刻辞职，你怎么看？”），获取反驳意见。
  - **Round 3**：NestJS 将前两轮的聊天记录打包，发给 Bot C（律师），让其做最终的风险总结。
  - _可行性优势_：这种架构让你对辩论流程有**绝对的控制权**，且能完美实现前端的实时打字机效果。

#### 2. WebSocket 房间与用户隔离机制 (Socket.io + NestJS)

- **多求助者同时进行的区分**：
  - NestJS 使用 `@WebSocketGateway()`。当求助案子生成时，MySQL 会产生一个 `roomId`（如 `room_101`）。
  - 无论谁进入这个案子的详情页，前端都会发送 `socket.emit('joinRoom', { roomId: 101 })`。
  - NestJS 执行 `client.join('room_101')`。当 NestJS 收到 Coze 返回的流式数据时，只调用 `server.to('room_101').emit('agentMessage', data)`。这样，100个案子同时进行也互不干扰。
- **求助者与吃瓜群众的区分**：
  - 用户登录后，前端持有 JWT Token。
  - 建立 WebSocket 连接时，NestJS 解析 Token 拿到 `userId`。
  - NestJS 查询数据库：如果 `userId === room.ownerId`，则标记该 Socket 连接为 `owner`（拥有打断辩论、补充案情的高级权限）；否则标记为 `viewer`（只能发弹幕、投票）。

4. **核心页：沉浸式辩论庭 (Live Debate Room) —— \*\*\***毕设最高分页面\*\*\*
   1. **左侧栏**：案件详情与关键证据（求助者可随时补充）。
   2. **中栏（AI 辩论主舞台）**：类似群聊界面。Bot A 发言时，头像亮起并显示“正在输入...”，随后流式输出文字。

   1. 辩论结束后生成。展示 AI 律师给出的最终《多维行动指南》和胜出方。
6. **AI 陪审员图鉴 (Agent Gallery)**：
   1. 展示平台上所有 AI 的“人设卡片”、胜率、历史高赞金句。
7. **个人主页 (Profile)**：
   1. 我发布的案件、我参与投票的案件。
   2. **赛博性格诊断图**：根据用户历史投票倾向，生成雷达图（如：偏向理性 80%、偏向共情 20%）。
8. **后台管理页 (Admin Dashboard - 可选，加分项)**：
   1. 用于封禁违规言论、管理房间状态。

### 三、 潜在难点与攻克方案（答辩防身指南）

在实际开发中，你会遇到以下 3 个主要技术难点，请务必按照我的方案解决：

#### 难点 1：如何处理 AI 的流式输出（Streaming）并广播给前端？

- **问题**：Coze API 返回的是 Server-Sent Events (SSE) 流式数据。如果 NestJS 等到全部接收完再发给前端，用户要等很久，体验极差。
- **解决方案**：
  - NestJS 使用 `axios` 或 `fetch` 请求 Coze API，并设置 `responseType: 'stream'`。
  - 监听 data chunk，每收到一个字或一句话，立刻通过 WebSocket `server.to(roomId).emit('stream_chunk', { agentId: 1, text: '...' })` 转发给前端。
  - React 前端维护一个状态 `const [messages, setMessages] = useState([])`，收到 chunk 后动态拼接字符串，实现打字机效果。

#### 难点 2：多智能体辩论时的“上下文记忆”如何管理？

- **问题**：Bot B 需要反驳 Bot A，它怎么知道 Bot A 说了什么？
- **解决方案**：
  - 不要依赖 Coze 自身的会话历史（因为你是用不同的 Bot）。
  - **由 NestJS 维护全局上下文**。在 MySQL 中设计一张 `RoomContext` 表，或者直接在 Redis/内存中维护一个数组。
  - 当调用 Bot B 时，NestJS 将之前的对话拼接进 Prompt 中发给 Coze。例如：`"用户的问题是：[xxx]。刚才毒舌说：[yyy]。请你作为共情者，反驳毒舌的观点并给出你的建议。"`

#### 难点 3：高并发下的投票数据一致性（Prisma 踩坑点）

- **问题**：几百个吃瓜群众同时点击“支持毒舌”，如果直接 `update vote = vote + 1`，容易产生并发覆盖问题。
- **解决方案**：
  - 在 NestJS 中，使用 Prisma 的原子操作（Atomic Operations）：
    ```TypeScript
    await prisma.agentStats.update({
      where: { roomId_agentId: { roomId: 1, agentId: 'bot_A' } },
      data: { votes: { increment: 1 } }
    });
    ```
  - 更新成功后，通过 WebSocket 广播最新的票数，前端 React 动态渲染进度条动画。

### 四、 数据库 Prisma Schema 核心设计参考

为了支撑上述逻辑，你的数据库设计应该精简而高效：

```Plain
model User {
  id        Int      @id @default(autoincrement())
  username  String   @unique
  password  String
  role      String   @default("USER")
  rooms     Room[]   // 发布的案件
  votes     Vote[]   // 投票记录
}

model Room {
  id          Int       @id @default(autoincrement())
  title       String
  content     String    @db.Text
  status      String    @default("WAITING") // WAITING, LIVE(辩论中), CLOSED(已结案)
  ownerId     Int
  owner       User      @relation(fields: [ownerId], references: [id])
  agents      Json      // 存储选中的AI列表，如 ["bot_A", "bot_B", "bot_C"]
  messages    Message[]
  createdAt   DateTime  @default(now())
}

model Message {
  id          Int      @id @default(autoincrement())
  roomId      Int
  room        Room     @relation(fields: [roomId], references: [id])
  senderType  String   // "AI" 或 "HUMAN"
  senderId    String   // 用户ID 或 BotID
  content     String   @db.Text
  createdAt   DateTime @default(now())
}

model Vote {
  id        Int      @id @default(autoincrement())
  userId    Int
  user      User     @relation(fields: [userId], references: [id])
  roomId    Int
  agentId   String   // 投给了哪个Bot
  @@unique([userId, roomId]) // 防止同一个用户在一个房间重复投票
}
```
