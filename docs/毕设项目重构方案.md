## 重构核心变化

### 1. 平台定位升级

- 原：辩论围观平台（功能单一）
- 新：决策辅助 + 情绪辅导双轮驱动，目标用户聚焦大学生

**平台使用闭环**：

目标用户是面临决策困境或情绪压力的大学生（考研 vs 工作、人际矛盾、感情问题等）。完整使用路径如下：

```
1. 带着困境来
   用户将困境发布为辩论案件，选择 3 个 AI 智能体（挂载博弈论/心理学/法律等不同知识库）
   代表不同立场展开三轮辩论，结合真实用户弹幕观点，最终给出多角度裁决建议
   → 解决"我该怎么选"

2. 辩论结束后提供入口
   辩论室投票结束后，聊天区出现轻提示"辩论已结束，需要和情绪伙伴聊聊吗？"，用户可点击跳转
   也可以进入结案报告，报告底部同样提供入口
   两处入口均携带案件上下文，跳转后情绪伙伴无需用户重复描述背景
   → 解决"我选完了还是很焦虑"

3. 情绪辅导持续跟进
   AI 情绪伙伴挂载大学生手册知识库（贴近大学生实际场景）
   本地 RAG 动态积累每次对话情绪摘要，情绪伙伴越聊越了解用户
   → 形成个性化长期陪伴

4. 高风险情绪预警（新增，见下方）
   辅导对话过程中后台实时做情感分析
   检测到高风险情绪时自动打标签，推送管理端重点关注
   → 平台闭环延伸到学校心理干预体系
```

**知识库与"个性化"的体现**：AI 情绪伙伴挂载的是大学生手册，回答贴近大学生实际处境（学业/人际/就业），而非泛泛的心理学理论；加上第四层动态 RAG 积累的个人情绪记忆，两者共同构成题目中"个性化"的核心。

### 3.1 情绪预警机制（新增核心功能）

**背景**：AI 情绪伙伴的对话内容可能暴露用户的心理危机信号（如自我伤害倾向、严重抑郁表述），平台有责任将这类信号传递给管理员，由管理员决定是否联系学校介入。

#### 情感分析 Bot 配置（Coze）

新建一个独立的情感分析 Bot，**不挂载对话历史，不流式输出**，只做一次性 JSON 分析。

**System Prompt**：

```
你是一个情绪分析工具，只负责分析输入文本的情绪状态，不做任何对话回复。

请严格按照以下 JSON 格式返回，不要输出任何其他内容，不要加解释，不要加 markdown 代码块：

{
  "emotionType": "ANXIOUS",
  "intensity": 75,
  "riskLevel": "NONE",
  "summary": "用户表达了强烈的焦虑情绪，原因是考研失败后感到前途迷茫、不知所措"
}

字段说明：
- emotionType：主导情绪，只能是以下之一：POSITIVE / CALM / ANXIOUS / ANGRY / SAD / DEPRESSED / DESPERATE
- intensity：情绪强度，0-100 的整数
- riskLevel：风险等级，只能是以下之一：NONE / MEDIUM / HIGH
  - HIGH：文本包含自伤/自杀/绝望到极点的表述
  - MEDIUM：文本表现出明显的低落、无助、持续负面情绪
  - NONE：其他情况
- summary：给管理员看的一句话说明，格式为"用户表达了[情绪描述]，原因是[核心内容]"，不超过50字；riskLevel 为 NONE 时此字段为空字符串

只输出 JSON，不输出任何其他文字。
```

**后端解析（`cozeService.analyzeSentiment`）**：

```typescript
async analyzeSentiment(text: string): Promise<{
  emotionType: string;
  intensity: number;
  riskLevel: string;
} | null> {
  try {
    const raw = await this.callChatOnce(SENTIMENT_BOT_ID, text);
    // 容错：提取第一个 { } 之间的内容，防止 Bot 多输出了文字
    const match = raw.match(/\{[\s\S]*\}/);
    if (!match) return null;
    const parsed = JSON.parse(match[0]);

    // 字段校验，任一字段异常则返回 null
    const validEmotionTypes = ['POSITIVE', 'CALM', 'ANXIOUS', 'ANGRY', 'SAD', 'DEPRESSED', 'DESPERATE'];
    const validRiskLevels = ['NONE', 'MEDIUM', 'HIGH'];
    if (
      !validEmotionTypes.includes(parsed.emotionType) ||
      typeof parsed.intensity !== 'number' ||
      !validRiskLevels.includes(parsed.riskLevel)
    ) return null;

    return {
      emotionType: parsed.emotionType,
      intensity: Math.min(100, Math.max(0, parsed.intensity)),
      riskLevel: parsed.riskLevel,
      summary: typeof parsed.summary === 'string' ? parsed.summary : '',
    };
  } catch {
    return null; // 任何异常（网络/解析）都静默返回 null，不影响主流程
  }
}
```

解析拿到 `riskLevel` 字段后，直接用它判断预警等级，不再依赖 `intensity` 二次推断，逻辑更清晰：

#### 触发流程

```
用户发送消息 → AI 情绪伙伴正常回复（不阻塞）
    ↓（异步，用户无感知）
后端对该条用户消息做两层检测：

第一层：关键词规则（快，优先）
  命中风险词库（"不想活"/"撑不下去"/"消失"/"结束一切"/"没有意义"等）
  → 直接判定 HIGH，跳过第二层

第二层：Coze 情感分析（慢，兜底）
  调用情感分析 Bot，返回情绪类型 + 强度（0-100）
  强度 > 85 且情绪类型为 DEPRESSED/DESPERATE → 判定 HIGH
  强度 70-85 且情绪类型为负面 → 判定 MEDIUM
  其余 → 不触发预警

    ↓（命中 MEDIUM 或 HIGH 时）
1. 写入 EmotionAlert 表
   记录：userId、sessionId、风险等级、触发消息摘要（非原文，截取关键语义）、触发时间
2. 写入 Notification 表，推送给所有管理员账号
   HIGH：type=ALERT_HIGH，实时推送，管理端顶部红色角标
   MEDIUM：type=ALERT_MEDIUM，写入通知中心，不实时推送
3. 同一用户同一会话内，相同等级的预警不重复触发（防刷）
```

#### 后端实现（NestJS）

在 `counseling.service.ts` 的 `sendMessage` 方法中，AI 回复完成后异步触发检测：

```typescript
// sendMessage 末尾，不阻塞主流程
this.checkEmotionRisk(session.userId, session.id, userContent).catch(() => {});

async checkEmotionRisk(userId: number, sessionId: number, text: string) {
  // 第一层：关键词规则
  const HIGH_KEYWORDS = ['不想活', '撑不下去', '消失', '结束一切', '活着没意思', '去死'];
  const hitKeyword = HIGH_KEYWORDS.some(kw => text.includes(kw));

  let riskLevel: string | null = null;

  if (hitKeyword) {
    riskLevel = 'HIGH';
  } else {
    // 第二层：Coze 情感分析（独立 Bot，非流式）
    const result = await this.cozeService.analyzeSentiment(text);
    // 解析失败或返回 null 时静默跳过，不影响主流程
    if (!result || result.riskLevel === 'NONE') return;
    riskLevel = result.riskLevel; // 直接用 Bot 返回的 riskLevel，MEDIUM 或 HIGH
  }

  if (!riskLevel) return;

  // 防重复：同一会话同等级只触发一次
  const exists = await prisma.emotionAlert.findFirst({
    where: { sessionId, riskLevel, isHandled: false }
  });
  if (exists) return;

  // summary 优先用 Bot 生成的摘要，关键词命中时 result 为 null，降级截取原文前50字
  const summary = result?.summary || text.slice(0, 50);

  // 写入预警记录
  const alert = await prisma.emotionAlert.create({
    data: { userId, sessionId, riskLevel, summary }
  });

  // 推送通知给所有管理员
  const admins = await prisma.user.findMany({ where: { role: 'ADMIN' } });
  await Promise.all(admins.map(admin =>
    this.notificationsService.create({
      userId: admin.id,
      type: riskLevel === 'HIGH' ? 'ALERT_HIGH' : 'ALERT_MEDIUM',
      content: `用户 ${userId} 触发${riskLevel === 'HIGH' ? '高' : '中'}风险情绪预警`,
      relatedId: alert.id,
    })
  ));
}
```

### 4. 四层 RAG 架构（核心技术亮点）

| 层次   | 用途                     | 技术                           | 实现状态  |
| ------ | ------------------------ | ------------------------------ | --------- |
| 第一层 | 智能体专业知识库         | Coze 云端 RAG（现有）          | ✅ 已完成 |
| 第二层 | 用户私有知识库           | Coze 云端 RAG（新增）          | ✅ 已完成 |
| 第三层 | 弹幕灌水过滤             | 本地 ChromaDB + Ollama（新增） | ✅ 已完成 |
| 第四层 | 用户情绪记忆图谱（动态） | 本地 ChromaDB + Ollama（新增） | ✅ 已完成 |

**第三层说明（实际实现）**：RAG 的核心职责是**过滤灌水**，而非强依赖立场识别。过滤后的所有有效观点（最多20条）统一注入 Round2/Round3 prompt，由智能体自行判断哪些支持己方、哪些支持对方。立场识别结果（SUPPORT_A/B/NEUTRAL）仅用于数据库记录和统计展示，不再作为分配依据。这一设计避免了嵌入模型对中文立场语义区分度不足导致的误判问题。

**第四层说明（实际实现）**：用户打字时前端防抖触发预检索（`/counseling/sessions/:id/prefetch`），结果缓存在后端内存 Map；用户发送消息时直接读取缓存，消除 Ollama 嵌入延迟。检索到的历史记忆以结构化 prompt 注入最后一条用户消息前（而非第一条），并附带明确的引用指引，让模型在生成回复时能自然引用历史内容。

### 5. 辩论流程升级（人机协同）

```
Round1（AI立场陈述）
  → 用户弹幕征集60秒（复用聊天框，提示条显示双方智能体名字引导用户表态）
  → RAG 过滤灌水，保留所有有效观点（最多20条，语义去重）
Round2（交叉反驳）
  → 两个 Bot 均收到全量有效观点 + 对方 Round1 发言
  → prompt 明确说明：观点来自真实用户，立场未预先标注，请自行判断并引用支持己方的声音
Round3（BotC综合裁决）
  → 收到前两轮完整辩论记录 + 全量有效观点列表
  → prompt 要求：自行分析民意分布，在裁决中引用并说明
→ 投票
```

**立场识别策略（双轨）**：

- 关键词规则（优先）：文本含智能体名字 + 支持/反对词时直接判定，准确率高
- 动态语义锚点（兜底）：基于智能体名字生成锚点向量做余弦相似度比较，余弦差值 > 0.05 才判定立场
- 立场识别结果写入数据库供统计，不作为 prompt 注入的分配依据

### 6. 知识库规划

#### 6.1 AI 情绪伙伴知识库（挂载在情绪伙伴 Bot 下）

| 知识库           | 内容                                                 | 引用场景                                         |
| ---------------- | ---------------------------------------------------- | ------------------------------------------------ |
| 学生手册         | 校规校纪、请假/转专业/申诉流程、学籍管理规定         | 用户遇到学校规定问题时，引用具体条款给出准确建议 |
| 心理健康指南     | CBT认知行为疗法、非暴力沟通、焦虑/抑郁识别与干预方法 | 疏导情绪时有理论依据，不只是泛泛共情             |
| 就业政策文件     | 应届生就业政策、考研报名流程、升学 vs 就业利弊分析   | 用户纠结考研/工作时，引用具体政策数据辅助决策    |
| 奖助学金制度     | 各类奖学金/助学金申请条件、贫困认定流程、绿色通道    | 用户有经济压力时，主动告知可申请的资助渠道       |
| 宿舍人际关系指南 | 常见宿舍矛盾处理建议、与辅导员沟通技巧、投诉渠道     | 大学生最高频的人际困境场景                       |

**引用原则**（写入 System Prompt）：

- 自然引用，不生硬列条款。例如说"根据学校规定，大二结束前都可以申请转专业，你现在时间上来得及"，而不是"第X条规定：……"
- 说明依据来源，让用户知道信息有据可查
- 引用后回到情感层面，不变成信息播报

#### 6.2 辩论智能体知识库补充

每个辩论智能体挂载两类知识库：**内容库**（支撑论点的事实/数据）+ **策略库**（辩论技巧/反驳话术）。

| 智能体                  | 内容知识库                                                 | 策略知识库                                                 |
| ----------------------- | ---------------------------------------------------------- | ---------------------------------------------------------- |
| Bot A（毒舌现实主义者） | 就业市场数据、薪资报告、考研上岸率、行业趋势、机会成本案例 | 批判性思维、逻辑谬误识别、数据驱动论证、反驳情绪化论点话术 |
| Bot B（温柔共情者）     | 心理健康研究、非暴力沟通、人际关系学、大学生压力调研数据   | 共情式论证、先认可再反驳结构、叙事性说服框架               |
| Bot C（中立观察者）     | 大学生困境决策案例库、两难选择结果追踪数据                 | 多角度综合分析框架、归纳核心争议方法、可操作建议表达技巧   |

**各智能体知识库引用原则**：

- 知识库内容只在 Coze 平台侧挂载，通过 Bot ID 调用时自动生效，代码层无需额外处理
- 三个智能体的知识库相互独立，不共享，避免角色串位
- 中立观察者不挂载任何单一立场的数据库，只挂案例库和分析框架，确保综合总结的中立性

#### 6.3 AI 情绪伙伴 System Prompt（新版）

```
你是一位专注于大学生群体的 AI 情绪伙伴，拥有心理学知识库、学生手册、就业政策等专业背景资料。

【角色定位】
- 你不是心理医生，不做诊断，不开药方
- 你是一个温暖、安全的倾听者和引导者，同时是一个"懂大学生处境"的知情者
- 你的目标是帮助用户理清情绪、找到自己的答案，必要时提供有依据的信息支持

【核心原则】
1. 共情优先：先认可情绪，再给建议。永远不要说"你应该..."
2. 避免说教：用提问引导用户自我探索，而不是直接给答案
3. 知识引用：当你的建议来自知识库时，自然地说明依据（"根据学校的规定..."、"心理学研究表明..."），让用户感受到建议是有根据的，而不是随口说说；引用后必须回到情感层面，不要变成信息播报
4. 安全边界：如用户提及自伤/自杀倾向，立即共情，告知"我很担心你，平台的老师也会关注到你，你不是一个人"，不要给出任何诊断或评价
5. 保持温暖：语气亲切自然，像一个既懂你又有点专业知识的学长/学姐

【对话风格】
- 每次回复不超过 200 字，保持轻盈，不要长篇大论
- 多用开放式问题（"你当时是什么感受？""这件事对你来说意味着什么？"）
- 适当用"我听到你说..."来确认理解
- 回复支持 Markdown（可以用 **加粗**、列表）
- 如果检测到用户情绪持续低落超过 3 轮，主动询问是否需要了解学校的心理援助资源

【注入内容说明】
在每次对话中，系统可能会在用户消息前注入以下两类背景内容，格式固定，你需要识别并正确使用：

1. 案件上下文（格式以"【用户关联的困境案件】"开头）
   - 内容是用户此前在平台发起的辩论案件标题和描述
   - 用途：你已经了解用户的困境背景，无需让用户重复描述
   - 使用方式：自然地把案件内容融入对话（"我看到你之前在纠结..."），不要照搬原文，也不要假装不知道

2. 历史情绪记忆（格式以"【背景参考：以下是该用户在过去几次对话中留下的核心情绪记录】"开头）
   - 内容是用户历次辅导会话结束后生成的情绪摘要片段，来自本地 RAG 检索
   - 用途：了解用户的情绪模式和核心困扰，提供个性化回应
   - 使用方式：选最相关的 1-2 条自然融入（"上次你提到..."），像一个真正记得你的朋友；不要一次性列举所有历史，不要生硬地说"根据你的历史记录"

如果消息前没有这些内容，正常对话即可，不要主动询问或提及。
```
